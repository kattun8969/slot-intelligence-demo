## 担当
| 担当 | 使命 | 提出先・完了条件 |
|---|---|---|
| ① 機種記事ライター | ③指定機種を調査・執筆し、WordPress用下書きHTML/コードと出典・条件を提出 | GitHub Issueを通じ②へ。公開操作はしない |
| ② 編集者（Work） | リコリコ基準に統一し、WordPress下書き・公開・表示・動作確認を実施する唯一の担当 | 本番URL、公開箇所の恒久アンカー、320/375px表示、更新履歴8件を記録 |
| ③ 総合ディレクター | 市場調査、優先順位、制作支援、ニュース原稿、収益化・効果測定 | ①へ機種制作を依頼し、②へニュース・広告素材を提出。実収益・公開実績を追跡 |

## ①の制作で守ること
- 機種ページの構成・スマホ表示はリコリコ完成見本と制作基準に合わせる。
- 期待値表は**オーナーが既に提供した添付資料の画像・表を最優先の根拠**とする。起点（AT/CZ/ボーナス/周期）、データカウンター/液晶表示、終了地点、貸出・交換条件、ゲーム数/pt/円、条件付き示唆を正確に区別。未確認数値の創作は禁止。
- 公式・解析サイト・SNS・PAPIMOを多角的に照合。PAPIMOの集計期間・サンプル・全設定混合の別、差枚とAT獲得枚数、機械割と設定別勝率の別を明示。
- 筐体画像、条件別期待値、PAPIMO、ゾーン/天井・短縮/やめ時、設定/モード示唆の不足を項目ごとに区分。独立して公開可能な部分は②へ先行提出。
- 権利処理が不明な購入資料原本・表の実質複製を公開IssueやPublic GitHubに掲載しない。

## ②Workの利用枠を節約する運用
- **毎時自動編集は停止中**。Workの別業務利用（18:00〜翌03:00 JSTの可能性）を妨げないよう、11時・16時の一括処理。追加起動は合意なく設けない。
- ①③が素材、画像の参照先、出典、適用条件、コード、変更範囲、検証条件をIssueで揃えてから②へ回す。
- ②は一回のWork作業で複数件を下書き→検証→公開。長期調査は③へ返す。WordPress接続確認を③が毎時繰り返す必要はない（#250）。
- 保存済みHTMLは静的な表示資料であり、WordPressのPHP、REST、投票連携の正常動作を証明しない。

## Issueの受け渡し記録
各Issueに最低限：対象機種/ページ、優先度、担当、現状（調査中/制作中/②編集待ち/公開済み/保留）、完成済みの独立公開可能範囲、残不足と依頼先、一次資料/出典と確認日、WordPress下書きコード/実装位置、期待値の適用条件、公開URLと検証結果、次に行う1手を記載する。

## 新スレッドへの引き継ぎ
1. 担当役割を決め、**本書、制作基準、公開方針、デザイン参照先**を読む。
2. 現在の未完了Issuesを確認して担当・期限・最新コメントと既提出素材を照合。旧チャットの記述だけを最新版と決めつけない。
3. 既存Issueを重複作成せず、最優先案件を継続する。提出物と結果は元Issueに戻す。
4. WordPressの公開完了は②による本番URL検証で判断。古いGitHub Pagesの状態を公開完了と混同しない。
5. 自動タスクはチャット移行だけでは移設されない。旧タスクを確認し、新旧の二重実行を防ぐ。
