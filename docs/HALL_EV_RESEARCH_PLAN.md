# 公開ホールデータから独自期待値を作るための検証手順（準備段階）

## 1. 収集前の確認
- 対象店舗/ホール名、データの公開範囲、保存・再利用の許諾、取得上限・アクセス頻度を確認する。禁止・不明の場合はAPI/スクレイピングを行わない。
- まず店舗から許諾を得たCSV、公開データの手動記録、または公式に提供されたAPIのいずれかを使う。ログイン回避・ボット対策回避をしない。
- ホール固有の **台番号は日ごとに機種・型式を確認** する。店舗間の同じ台番号は同一台と推定しない。交換率も店舗と日付で管理。
- 生データには個人情報・会員ID・ユーザーの行動追跡情報を含めない。

## 2. カウンターの読み方を監査する

| 表示名の例 | その表示だけで確定できない点 | 追加入手すべき根拠 |
|---|---|---|
| 大当り／初当り | AT/STなのかCZ/REGを含むか | 店舗のカウンター定義、台の履歴実測、機種仕様 |
| BB／RB／REG | 機種がボーナス契機ATか、天井カウンターをリセットするか | 対象型式、イベント時点、引継ぎ仕様 |
| CZ | 失敗時AT間Gが引き継がれるか | 連続履歴、対象機種の公開解析 |
| 駆け抜け／単発 | 上位ST終了、通常ST終了、単なる1連終了の区別 | AT/ST終了画面・払い出し・現場記録 |
| 差枚／差枚グラフ | 有利区間内差枚なのか、当日差枚なのか | データ提供元の仕様、リセット境界 |
| 朝一 0G | 設定変更後か据え置きか、前日分引継ぎか | ホール告知、前日当日履歴、リセット挙動 |
| 300pt／2周期 | データカウンターGとは一致しない | 実機液晶のポイントと周期、進行の起点 |

**未確認のラベルや状態を統計モデルに自動変換しない。** 見える台データと内部状態は別。

## 3. 監査用CSV形式
先頭行は以下の列名（必須）：

`venue_id,machine_model,model_revision,data_date,machine_number,counter_label,counter_value,counter_unit,event_label,event_order,source_url,collection_method,observation_confidence,rules_verified`

- `machine_model`: 機種名と`model_revision`型式を必ず照合
- `counter_label`: 店舗画面上の表示名をそのまま残す。単位（G/pt/cycle/times/medals/unknown）を分離
- `event_label`: 表示名の原文を保持。「駆け抜け」は未検証の主張として保留
- `event_order`: 1日のイベントの順序。時間が不明なら順序が確定できるデータだけ採用
- `collection_method`: `permitted_csv` / `manual_public_record` / `official_api`
- `observation_confidence`: `observed` / `inferred` / `unknown`
- `rules_verified`: 店舗・機種・型式のカウンター定義を照合済みなら`yes`、それ以外は`no`

`python3 scripts/audit_hall_counter_csv.py path/to/export.csv --output tmp/counter-audit.json`

初期段階ではレポートは**非公開**とし、GitHub Pagesにはアップロードしない。判定ができない行は`hold_for_review`、解釈が成立する行だけ`accepted`。この段階でも期待値は出さない。

## 4. 独自期待値表を作る順序
1. 台番号→機種・型式を日ごとに確認、時系列順序とイベント欠損を検査
2. 店舗のカウンター定義を照合し「AT間G、CZ間G、ボーナス間G、周期、スルー」の起点を別列で構築
3. 終了判定と閉店打ち切りを別扱いし、履歴のない駆け抜け・リセット・差枚の断定を禁止
4. 台日・時点を単位に台候補を構成し、特定状態で開始できた場合を独立した検証集団とする
5. 投資と獲得、コイン持ち、純増、交換率、やめどき、閉店リスクを区別し、実戦値から再計算する
6. サンプル数、推定値、ばらつき、追跡不能・欠損率、日別/店舗別の偏りを同時掲載
7. 同一店舗の過去データで調整し、新しい日付・別店舗で外部検証。設定1と断定できない公開ホールデータを「設定1確定」と扱わない
8. サンプルが少ない区間は「未推定」。優遇冷遇の影響は対照条件が揃って初めて検証、推測のみで補正しない

## 5. 公開期待値との比較
- `docs/public-ev-reference.json` は他サイトの公開行を**条件とともに参照**する別モデル。元の機種仕様から独自に算出した額ではない。
- `docs/ev-simulator.html` は設定1スペックや仮の当選分布・獲得枚数で動かす**検証モデル**として維持。
- 将来の独自テーブルは「収集権限・条件正規化・試算仮定・実測件数・推定誤差」を保存した別ファイルから生成し、両者を混同しない。

## 6. 次に必要な入力
先行検証する店舗・公開データURL、利用規約または許諾、データカウンターの説明、可能な日別サンプル（抜粋CSV）。必要な基準を揃えた上で店舗・機種ごとに収集機能を実装する。

## 7. 実測データの充足率を先に確認する（2026-11-15実装）

CSV監査結果には、**店舗ID × 機種名 × 型式** ごとの `coverage` 集計を含めます。データ行数、条件確認済み件数、保留件数、収録日数、台番号数、観測イベント名、単位、曖昧な当選・駆け抜けの件数を出します。

`accepted_percent` は **データの読み取り条件を監査できた割合** であり、期待値の精度・サンプル数の十分さ・高設定割合ではありません。どのグループも `ev_ready: false` で始まります。

店舗カウンターの見かけ上の `当り`、`単発`、`駆け抜け` だけでST当否や状態遷移を復元したり、日別差枚から特定条件の投資を作り出したりしません。まず元画面と実際の履歴を対照し、投入・払出・稼働開始点などの連続データを確認してください。

独自期待値を生成できる条件が揃うまでは、監査結果をサイトの機種ページへ自動反映しない運用です。
